Децентрализованные коммуникации зависят от независимо управляемых узлов, которые проверяют, обмениваются и сохраняют данные. ADAMANT node v0.11.1 — это обновление, направленное на повышение безопасности и надежности, которое укрепляет повседневные операции, сохраняя при этом существующие правила консенсуса протокола. Это первый помеченный релиз в линейке v0.11; код v0.11.0 был слит, но не имел тега, а v0.11.1 включает дополнительное исправление сетевого взаимодействия между узлами, поэтому операторам, уже использующим этот код, следует обновиться.

### Сокращение поверхности атаки

В этом релизе удалены устаревшие элементы управления формированием блоков (forging) по HTTP и конечные точки среды выполнения DApp. Эти поверхности включали пути исполнения и подписи на стороне сервера, которые больше не соответствуют современным требованиям к узлу. Их удаление устраняет уязвимость, описанную в бюллетене GHSA-vjhq-r5fg-85cx, и делает границы эксплуатации узла более понятными. Делегаты теперь настраивают формирование блоков через `forging.secret` и применяют изменения с помощью корректной перезагрузки. Дополнительные локальные CLI-команды позволяют разблокировать и заблокировать зашифрованные парольные фразы. API DApp, работающие в режиме только для чтения, и обработка консенсуса для существующих типов транзакций DApp остаются доступными; клиентам следует подписывать транзакции локально и отправлять их через стандартные конечные точки транзакций.

### Зашифрованные секреты делегатов

Операторы теперь могут шифровать парольные фразы для формирования блоков с помощью пароля оператора, используя алгоритмы AES-256-GCM и scrypt. Конфигурация в открытом виде остается совместимой для существующих развертываний. Узел с зашифрованными секретами по-прежнему может синхронизироваться, поддерживать связь с узлами, обслуживать API и обрабатывать свой пул памяти (mempool), пока формирование блоков заблокировано. После каждой перезагрузки оператор разблокирует формирование блоков через локальный запрос или Unix-сокет управления, доступный только владельцу. Поддержка мониторинга позволяет операторам наблюдать за состоянием блокировки, не раскрывая личность делегата. Шифрование защищает сохраненные парольные фразы, но не снимает с оператора ответственности за безопасность хоста, пароля, резервных копий и доступа.

### Сетевая отказоустойчивость

Промышленные ограничения по защите от злоупотреблений (anti-abuse) для HTTP и WebSocket включены по умолчанию. Они охватывают публичные API, трафик между узлами, попытки подключения и подписки, с документированным ответом HTTP 429 для запросов, превышающих лимиты. Существует важное предостережение для смешанных версий: устаревшие узлы, которые не отправляют заголовок согласования лимитов, обходят внутренние HTTP-ограничения узла во время перехода. Операторам следует принудительно устанавливать внешние ограничения на `/peer/*` на своем обратном прокси-сервере или брандмауэре. Существующие конфигурации, которые явно содержат устаревшие настройки `max: 0`, сохраняют соответствующие лимиты отключенными до их обновления.

Релиз также ограничивает проверки работоспособности узлов, более обдуманно обрабатывает недоступные узлы и улучшает восстановление PostgreSQL после потери соединения. Скрипты установки и восстановления теперь проверяют снимки (snapshots) перед стандартным путем замены базы данных, используют установку зависимостей на основе файлов блокировки (lockfile) и более осторожно перезапускают узел во время синхронизации или перестроения.

### Восстановление соединений с узлами в реальном времени

Финальное исправление v0.11.1 восстанавливает выбор исходящих WebSocket-соединений с узлами. В коде v0.11.0 без тегов отсутствующие значения по умолчанию для объектов активных узлов приводили к тому, что запрос кандидатов не возвращал узлы. Узлы по-прежнему могли синхронизироваться по HTTP и принимать входящие WebSocket-соединения, но исходящая передача блоков и транзакций в реальном времени не работала. Исправление устанавливает значения по умолчанию для экземпляра активного узла, а регрессионные тесты охватывают значения по умолчанию и запрос выбора.

### Корректность повторов и более строгие API

Урегулирование раундов теперь учитывает текущую высоту блока во время повтора (replay), а индексация вознаграждений при откате сопоставляет каждого делегата с его собственными изменениями. В примечаниях к релизу сообщается о проверках эквивалентности состояния «бит-в-бит» в основной сети (mainnet) и тестовой сети (testnet) при полном перестроении, запуске образа и восстановлении из контрольной точки. Отдельная ранее существовавшая проблема отката остается отслеживаемой в задаче #300.

Для разработчиков приложений обработка фильтров для состояний, чатов и комнат чатов стала более строгой. Поддерживаемые фильтры `and:` применяются последовательно; неподдерживаемые фильтры `or:` и ранее игнорировавшиеся параметры отклоняются. Параметр пакетного ключа изменен с `keysIds` на `keyIds`. Это намеренные критические изменения HTTP API, поэтому интеграции следует проверить перед развертыванием.

### Единая документация

Документация узла и спецификация OpenAPI 3.2 теперь находятся вместе с кодом в репозитории узла, что позволяет обновлять поведение, документацию и контракт API одновременно. Операторы и разработчики могут изучить единую [документацию](https://docs.adamant.im/) и [схему API](https://docs.adamant.im/schema/), включая новые руководства по обновлению, безопасности, мониторингу и тестированию.

### Примечания по обновлению

Обновление не вводит форк консенсуса и не требует новых SQL-миграций. Сериализация блоков и транзакций, подписи, порядок делегатов, вознаграждения, комиссии, высоты активации и тайминги слотов остаются такими же, как в v0.10.2. Обновление требует внимания к операционной совместимости и совместимости HTTP API. Операторам следует прочитать [руководство по обновлению](https://docs.adamant.im/own-node/upgrading.html) и проверить интеграции на наличие удаленных маршрутов и более строгих фильтров. Требуется поддерживаемая версия Node.js: `^22.22.2 || >=24.15.0`. Корректно остановите узел и дождитесь завершения очистки, затем проверьте лимиты запросов, доверие к прокси и конфигурацию формирования блоков перед перезапуском. Если секреты формирования блоков зашифрованы, разблокируйте их после каждой перезагрузки и проверьте локальное состояние блокировки. После обновления проверьте статус узла, подключение к узлам и настройки защиты от злоупотреблений.
