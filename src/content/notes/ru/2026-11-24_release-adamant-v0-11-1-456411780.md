ADAMANT blockchain node v0.11.1 — это важный релиз, направленный на повышение безопасности и надежности для операторов узлов, делегатов, операторов пулов, обозревателей, мессенджеров и разработчиков сервисов. В этом обновлении удалены устаревшие API управления форжингом и средой выполнения DApp (устранение уязвимости GHSA-vjhq-r5fg-85cx), добавлена возможность шифрования паролей делегатов, включены производственные лимиты защиты от злоупотреблений для HTTP и WebSocket, усилены скрипты установки и восстановления, исправлены проблемы с надежностью PostgreSQL, пиров и расчетов раундов, а также перенесена документация и спецификация OpenAPI 3.2 в этот репозиторий.

v0.11.1 — это первый опубликованный релиз линейки v0.11. Код v0.11.0 был слит в ветку master 23 ноября 2026 года, но не имел тега. v0.11.1 содержит одно дополнительное сетевое исправление, поэтому операторам, уже использующим v0.11.0 из master, рекомендуется обновиться.

Обновление настоятельно рекомендуется для повышения безопасности, надежности работы, а также для приведения API и документации в актуальное состояние. Данный релиз не вносит изменений в консенсус и не требует SQL-миграций. Сериализация блоков и транзакций, подписи, порядок делегатов, вознаграждения, комиссии, высоты активации и тайминги слотов остались такими же, как в v0.10.2. Однако присутствуют критические изменения в HTTP API; перед обновлением обязательно ознакомьтесь с руководством: https://docs.adamant.im/own-node/upgrading.html

## Что нового в v0.11.1

В релизе v0.11.0 присутствовала регрессия: объекты активных пиров не имели свойства `syncProtocol`, из-за чего вызов `peers.list({ syncProtocol: 'http' })` в WebSocket-клиенте не возвращал кандидатов. Узлы не устанавливали исходящие WebSocket-соединения и при каждом обновлении записывали в лог `No suitable peers found for WebSocket connections`. Синхронизация по HTTP и входящим WebSocket продолжала работать, но передача блоков и транзакций в реальном времени через исходящие WebSocket была нарушена. Теперь `Peer.accept()` устанавливает значения по умолчанию `syncProtocol: 'http'` и `isBroadcastingViaSocket: false` для экземпляра. Регрессионные тесты покрывают как значения по умолчанию для Peer, так и корректность запроса `getRandomPeers()`.

В руководство по обновлению добавлен раздел для v0.11.1 и примечания по мониторингу. Стандартный `sudo` в Ubuntu 25.10 (`sudo-rs`) отклоняет `Defaults:zabbix !requiretty` из примера файла sudoers, поэтому пути к интерпретатору nvm должны быть обновлены одновременно в обертке Zabbix и в правиле sudoers.

## Безопасность и усиление защиты узла

Устаревшие интерфейсы управления форжингом и средой выполнения DApp были полностью удалены, что исключает возможность выполнения кода на стороне сервера, пути для загрузки/распаковки/npm/песочницы и проксируемые HTTP-маршруты управления форжингом, вместо попыток исправления аутентификации для устаревших компонентов.

Теперь поддерживается опциональное шифрование паролей делегатов. Операторы могут зашифровать записи `forging.secret` с помощью пароля оператора (`admnode-enc-v1.`, AES-256-GCM плюс асинхронный scrypt с N=131072, r=8, p=1) через `npm run adm-node -- forging encrypt|unlock|lock|status`, сохраняя при этом полную совместимость с открытым текстом. Узлы с зашифрованными секретами остаются полностью функциональными (синхронизация, пиры, API, mempool), а форжинг остается заблокированным до тех пор, пока не будет разблокирован через TTY при запуске или через локальный Unix-сокет управления, доступный только владельцу (проверяется канонический путь к директории, владелец, права доступа и inode; пароли никогда не принимаются через аргументы командной строки или переменные окружения). Релиз включает исправленную обертку `tools/zabbix/` с белым списком, правила sudoers, `UserParameter` и шаблоны Zabbix 7.0, которые выводят JSON состояния локальной блокировки (`loading`, `disabled`, `locked`, `partial`, `unlocked`, `unavailable`) и отдельные публичные проверки пропущенных блоков/продуктивности.

Производственные лимиты защиты от злоупотреблений теперь включены по умолчанию. Ограничения по IP (IPv6 /56-группировка) и классу маршрута действуют в 60-секундном окне: Public REST `/api/*` (15300 агрегированно; status: 12000, read: 3000, publish: 300, исключая CORS OPTIONS preflight) и Peer HTTP `/peer/*` (44000 агрегированно; status: 20000, sync: 12000, broadcast: 12000, с фиксированным HTTP 429 и согласованием `X-Adamant-Rate-Limit: 1`, чтобы обновленные пиры корректно ограничивались без бана). В v0.11.0 запросы `/peer/*`, не содержащие `X-Adamant-Rate-Limit: 1`, пропускают как жесткие лимиты, так и замедление, поэтому пиры v0.10.x не отключаются во время обновлений. Поскольку вызывающая сторона управляет этим заголовком, враждебные клиенты, не передающие его, не ограничиваются внутри узла на `/peer/*` (включая `GET /peer/blocks`); операторам следует применять внешние лимиты на `/peer/*` на уровне обратного прокси или брандмауэра. Лимиты WebSocket-клиента (`wsClient.limits`) для пулов активных/ожидающих соединений, окон попыток подключения, лимитов на сокет по адресу/типу/подтипу чата и окон подписки применяются вместе с лимитами рукопожатий Node WebSocket (`wsNode`) на IP и на nonce.

Скрипты установки и восстановления были усилены. Общие вспомогательные функции были вынесены в `tools/lib/adamant_node_common.sh` с покрытием модульными тестами и проверкой CI ShellCheck. Скрипты генерируют файлы экосистемы PM2 с `kill_timeout: 120000` и абсолютным путем к интерпретатору nvm; отказываются перезапускать синхронизирующиеся/загружающиеся/перестраивающиеся узлы без флага `-f`; и устанавливают systemd drop-in (`After=`/`Wants=` PostgreSQL и Redis, `TimeoutStopSec=180`, `LimitCORE=0`). Они требуют независимой проверки SHA-256 и `gzip --test` перед восстановлением снапшотов; `fix_node.sh` проверяет снапшоты перед удалением базы данных по умолчанию (`-d` для явного удаления) и устанавливает зависимости с помощью `npm ci --omit=dev` с зафиксированными версиями npm/PM2/logrotate.

Зависимости были обновлены после 7-дневного карантина. Релиз добавляет `.npmrc` `min-release-age=7` и `scripts/checkDependencyQuarantine.js`, применяемые в CI как для корневого `package-lock.json`, так и для `docs/package-lock.json`. Проверенные `allowScripts` были зафиксированы (`libpq@1.11.0: true`, `javascript-obfuscator: false`), а зависимости обновлены с 0 умеренных/высоких/критических уязвимостей (остались только 3 существующие низкие уязвимости в зафиксированных `bitcore-mnemonic`/`bitcore-lib`/`elliptic`).

## Обновления API и WebSocket

Улучшена корректность фильтрации состояний, чатов и комнат. Фильтры с префиксом `and:` сопоставляются корректно, `toHeight` (`b_height <= toHeight`) применяется в `/api/states/get` и `/api/chats/get`, исправлена ошибка общего SQL-плейсхолдера при комбинировании фильтров отправителя/получателя/участника, `keysIds` переименован в `keyIds` с проверкой 20-символьного KVS `key`, а неподдерживаемые `or:` и неприменяемые поля теперь отклоняются.

Введен стандартизированный контракт `429 Too Many Requests`, возвращающий `{"success": false, "error": "..."}` с заголовками `Retry-After`, стандартными `RateLimit-*` (включая `RateLimit-Scope`), опциональными устаревшими `X-RateLimit-*` и поддержкой CORS.

Исправление ротации исходящих WebSocket-пиров сбрасывает `syncProtocol` в `http` перед закрытием исходящих WS-сокетов во время ротации/ре-инициализации, поэтому `connectedPeers` больше не исчерпывает пул кандидатов.

## Надежность узла, база данных и сетевое взаимодействие

Проверки состояния исходящих пиров и лимиты ответов транспорта теперь ограничены. Установлены лимиты на цели зондирования за цикл (`maxProbeTargets: 20`, `unverifiedProbeLimit: 5`), конкурентность (`updateConcurrency: 8`), интервалы (`probeSpacingMs: 50`) и размер таблицы пиров (`maxPeers: 500`). При сетевых ошибках применяется экспоненциальная задержка (от 30 с до 1 ч), а недоступные пиры (не являющиеся seed) удаляются после 6 последовательных сбоев (с учетом 24-часового льготного периода и `minConnectedPeers: 10`). Лимиты ответов исходящих пиров ограничены по эндпоинтам, чтобы покрыть худшие случаи расширения JSON (256 МБ для `/peer/blocks`, 32 МБ для `/peer/transactions`, 2 МБ для `/peer/signatures`, 256 КБ для `/peer/list`, 64 КБ для подтверждений статуса/широковещания) без удаления пиров при ошибках лимита синхронизации. Потоковые `sync` запросы допускают до `max(peers.options.timeout, 270000)` мс для `/peer/blocks` (чуть меньше `constants.syncStallTimeout`) и `max(peers.options.timeout, 60000)` мс для других `sync` эндпоинтов, откладывая только область `sync` на 30 с при прерывании потокового дедлайна без глобальной задержки сетевой ошибки, сохраняя при этом `peers.options.timeout` как таймаут неактивности сокета и дедлайн для `status`/`broadcast`.

Улучшено восстановление соединений с PostgreSQL. Клиенты с ошибками подключения помечаются как фатальные, поэтому `pg-promise` закрывает и заменяет их. Разрывы соединений в пуле логируются, добавлены `connectionTimeoutMillis` (10 с), TCP keepalive на чистом JS, маппинг `idleTimeoutMillis` и `query_timeout` (300 с) после миграции, чтобы разорванные соединения с БД не блокировали `sequence`.

Запрос защиты mem-checkpoint был оптимизирован путем замены полного объединения аккаунтов с блоками на `getSlotAccountsBlockAboveHeight(slot)`, сканирующий только блоки выше высоты чекпоинта. Обновлены seed-пиры для основной и тестовой сетей, указаны актуальные init-узлы и исправлен порт `43998` для `138.201.152.191`.

## Протокол, консенсус и расчет раундов

Добавлены `summedRound` с ограничением по высоте и индексация вознаграждений при откате. Запрос `AND b.height <= ${height}` добавлен в `sql/rounds.js#summedRound` (передается из `modules/rounds.js#sumRound`), чтобы повторное воспроизведение генезиса с высоты 1 не приводило к преждевременному расчету комиссий/вознаграждений из сохраненных блоков 2..101 до достижения высоты 101. Исправлен откат `logic/round.js#applyRound` (`backwards === true`), чтобы каждый делегат сопоставлялся напрямую с собственной записью `roundChanges.at(i)` без мутации `scope.roundDelegates`, что предотвращает некорректное вычитание вознаграждений при откатах раундов с промежуточными вознаграждениями. Эквивалентность состояний «бит-в-бит» проверена в основной и тестовой сетях при полной перестройке с высоты 1, запуске образа и восстановлении из чекпоинта. Отдельный существующий дефект отката `backwardTick` outsiders / `votesWeight` при изменении рейтинга топ-101 делегатов на границе раунда остается под наблюдением в #300.

Изменений в консенсусе и новых SQL-миграций нет. Сериализация транзакций/блоков, подписи, рейтинг делегатов, вознаграждения, комиссии, высоты активации и схема базы данных остались прежними с v0.10.2.

## Консолидация документации и OpenAPI

Документация VitePress и спецификация OpenAPI 3.2 были объединены непосредственно в `docs/` и `openapi/` внутри репозитория `Adamant-im/adamant`, что позволяет атомарно обновлять код, схему и документацию. Все инструменты документации/OpenAPI (`vitepress`, `@redocly/cli`, `swagger-ui-dist`) изолированы внутри `docs/package.json`, `docs/package-lock.json` и `docs/.npmrc` (`min-release-age=7`), сохраняя чистоту корневого `package.json`. Рабочий процесс GitHub Actions собирает и развертывает единый сайт GitHub Pages из ветки master (https://docs.adamant.im/ и https://docs.adamant.im/schema/ плюс `schema.json`), а CI проверяет, что `info.version` в `openapi/specification/openapi.yaml` совпадает с `version` в корневом `package.json` в PR, направленных в master. Вся документация для операторов/API и 50 операций OpenAPI обновлены для v0.11.0, добавлены новые `own-node/upgrading.md`, `own-node/security.md`, `own-node/monitoring.md` и `own-node/testing.md`, а `README.md`, `.github/CONTRIBUTING.md`, `tools/zabbix/README.md`, `AGENTS.md` и `AI_AGENT_NOTES.md` были оптимизированы. Downstream-проекты `Adamant-im/adamant-api-jsclient` и `Adamant-im/adamant-console` будут обновлены в рамках последующих работ для получения источников OpenAPI из `Adamant-im/adamant/openapi/`.

## Примечания по обновлению для операторов

Перед развертыванием обновите Node.js до `22.22.2+` (на ветке 22.x) или `24.15.0+`. Корректно остановите работающий узел (SIGINT/SIGTERM и дождитесь `Cleaned up successfully` — никогда не используйте `kill -9`). Установите производственные зависимости строго из lock-файла:

```
npm ci --omit=dev
```

Проверьте `config.json` и удалите устаревшие блоки `api.options.limits` и `peers.options.limits`, содержащие `max: 0`, чтобы унаследовать производственные значения по умолчанию v0.11.0 (или установите явные значения `limit` выше 0). Убедитесь, что `trustProxy` равен `true` только в том случае, если узел доступен исключительно через один непосредственный обратный прокси, перезаписывающий `X-Forwarded-For`. Удалите любую автоматизацию, вызывающую устаревшие HTTP-маршруты управления форжингом или DApp; управляйте форжингом через `forging.secret` с корректным перезапуском (и опционально шифруйте секреты с помощью `npm run adm-node -- forging encrypt`, обеспечив отсутствие прав на запись для группы/всех в директории checkout и настроив локальный мониторинг состояния блокировки Zabbix). Если вы используете зашифрованные пароли делегатов, разблокируйте форжинг после каждого перезапуска:

```
npm run adm-node -- forging unlock
```

В v0.11.x нет новых миграций базы данных. После перезапуска проверьте `/api/node/status`, сетевое взаимодействие пиров, лимиты защиты от злоупотреблений и (если используете зашифрованные секреты) `npm run adm-node -- forging status --json`.

## Производственная проверка

Перед этим релизом v0.11.0 работал на узле основной сети с 4 делегатами форжинга, использующими зашифрованные пароли (Ubuntu 26.04, Node.js 24.22.3, PM2), обновленный с v0.10.3 с помощью корректной замены директории. За 16+ часов было создано 471 блок без пропусков после перезапуска, высота синхронизирована с сетью, записи `ERR` отсутствовали, за исключением отказов консенсуса broadhash во время одного ~30-секундного догона после медленного тика раунда (проверка безопасности отказалась форжить при отставании; ни один блок не был потерян). Зашифрованный форжинг был проверен от начала до конца: `forging encrypt` с последующим корректным перезапуском и `forging unlock` через сокет управления во время состояния `loading`; шаблон состояния блокировки Zabbix и отдельные хосты результатов делегатов были проверены. Единственным предупреждением, специфичным для v0.11.0, была регрессия исходящих WebSocket, исправленная в v0.11.1.

### Критические изменения

Полное руководство по миграции для операторов: https://docs.adamant.im/own-node/upgrading.html

Устаревшие API управления форжингом и средой выполнения DApp были удалены (#295, GHSA-vjhq-r5fg-85cx). Устаревшие HTTP-маршруты управления форжингом (`enable`, `disable`, `status`, `enableAll`, `disableAll`) и устаревшие маршруты среды выполнения/исполнения/подписи/пиров DApp (установка, запуск, остановка, удаление, инспекция состояния, подпись/вывод на стороне сервера, динамические маршруты для DApp и маршруты среды выполнения пиров DApp) удалены. Форжинг теперь настраивается исключительно через `forging.secret` в `config.json` (с корректным перезапуском при изменениях) и опционально через локальный CLI `adm-node` для разблокировки/блокировки при использовании зашифрованных паролей. Устаревшие блоки конфигурации `forging.access` (`whiteList`) и `dapp` остаются загружаемыми для совместимости при обновлении, но игнорируются с предупреждением о депрекации при запуске. API DApp только для чтения и обработка консенсуса для типов транзакций DApp 5, 6 и 7 не изменились; клиенты должны подписывать транзакции локально и отправлять их через стандартные эндпоинты транзакций (`POST /api/transactions` / `POST /api/transactions/process`).

Строгая валидация фильтров только с `and:` теперь применяется к состояниям, чатам и комнатам (#294). В `/api/states/get` (GET и POST), `/api/chats/get` и `/api/chatrooms/*` фильтры с префиксом `and:` нормализуются до простых имен полей и комбинируются строго через AND. Фильтры с префиксом `or:` теперь отклоняются (`OR filters are not supported`) вместо того, чтобы игнорироваться. Ранее неприменяемые или ошибочно написанные параметры (включая `fromHeight`/`toHeight` и `userId` в запросе к `/api/chatrooms/*`, `blockId`, фильтры по метке времени/сумме/комиссии, `minConfirmations` и ошибочный `keysIds`) теперь отклоняются; пакетный поиск ключей состояний переименован из `keysIds` в `keyIds` с использованием 20-символьного формата KVS `key`. Конфликтующие простые значения и значения с префиксом `and:` также отклоняются.

Минимальная версия Node.js была повышена (#296). Требуемая среда выполнения теперь `^22.22.2 || >=24.15.0` (ранее `>=22.13.0`). Node.js `24.0.0–24.14.x` не поддерживается для инструментария разработки.

Производственные лимиты защиты от злоупотреблений включены по умолчанию (#292). `config.default.json` теперь включает ненулевые лимиты HTTP и WebSocket. Существующие файлы `config.json`, содержащие устаревшие `max: 0` в `api.options.limits` или `peers.options.limits`, сохраняют эту поверхность отключенной и записывают предупреждение при запуске; операторам следует удалить эти блоки, чтобы унаследовать значения по умолчанию v0.11.0, или настроить явные значения `limit` выше 0.
